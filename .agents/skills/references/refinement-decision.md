# A focused refinement decision

Use for a named Culmina product-design refinement that changes a meaningful
hierarchy, interaction or visual decision. Keep the record in the existing task,
review or PR; a new document is optional. A small alignment correction does not
need a full product study. The current user request sets scope and authorization.

Record enough to evaluate the proposed benefit:

| Question | Evidence to retain |
| --- | --- |
| What user problem are we addressing? | A concrete step in the planning or result-recording task and observed friction; label an untested concern as a hypothesis. |
| Why should this change help? | The intended improvement in comprehension, readability or action, and why the existing component/composition is insufficient. |
| What must stay true? | Relevant product/data invariants, state distinctions and actual source/caller; do not invent science or change calculations for appearance. |
| What counts as success? | Observable criteria appropriate to the task, such as full labels at the affected scaler, a reachable action, or users distinguishing time fit from saved state. Do not fabricate usability results or universal numerical thresholds. |
| Is the comparison fair? | Before/after with the same data, state, viewport, text scale, theme and fonts; disclose differences and synthetic fixtures. Missing baseline evidence remains a limit. |
| What was checked? | Relevant themes, phone constraints, large text, states and interactions. Keep source review, host renders, Android, screen reader and human judgment separate. Select checks from the actual change. |
| What was decided? | Accept, revise or reject, with the reason and remaining uncertainty. Record owner acceptance only when given; an agent recommendation is not owner approval. |

For reviews, report findings without implementing them. For authorized changes,
complete the scoped work and appropriate checks; this record adds no extra
approval gate. If a visual direction requires a user choice, retain the proposal
and the pending decision rather than presenting it as adopted.

The main outcome is whether the user can understand the viable night/target,
configure the plan, explain its fit, deliberately save it and later record the
actual result. Reuse current components and focused skills; the record does not
authorize a redesign, new toolchain or additional dependencies.
