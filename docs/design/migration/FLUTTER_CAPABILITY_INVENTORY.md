## Coverage beyond the eight web screens and specific adaptation gaps

1. **Night and Moon now have distinct roots** (`/night`, `/moon`) with one transient `NightBrowserViewModel`. The existing `/night` entry and explicit adoption remain. Focus/keyboard/native navigation verification is still row-specific (E4).
2. **Weather is tied to the plan night in the baseline.** The browser design's independently browsed condition context needs a deliberate UI-state adapter. Reusing the active plan's weather blindly for a viewed future date would mislabel real data. No additional weather provider is authorized.
3. **Rigs, targets and sites have separate manage/choose semantics.** Flattening Library into an attractive static list would remove the editors and selected-plan update rules. Retain existing editor and picker routes with minimal Hybrid presentation.
4. **Logbook includes far more than a list.** Entry snapshots, rename/delete, result recording, progress, text share, structured export and AstroBin preview must remain discoverable. The result form and progress destination are supporting screens even if absent from the initial eight.
5. **File workflows are not equivalent.** Native capture-file metadata import and storage calibration are real existing integrations. The web “capture-file walkthrough” cannot replace them. The owner explicitly declined a new standalone rig-JSON format; its omission is accepted, not implemented equivalence. Photo metadata and backup/restore remain separate existing native capabilities.
6. **Unknown/missing/partial states are functionality.** No-site, no rig/target, no dark window, unavailable future weather, stale forecast, unsupported metadata, incompatible database and persistence failures must remain actionable. Static demo values cannot fill these gaps.
7. **Settings affects Plan and Tonight through existing state.** Preserve defaults versus plan overrides and unsaved saved-plan transitions. Do not replace Settings with browser-local assumptions or a visual-only form.
8. **Existing platform surfaces extend beyond web.** First-run consent, native file/share pickers, restore/restart, Android Back/route restoration, keyboard and system bars require native checks. Host widget screenshots and browser captures do not establish their acceptance.
