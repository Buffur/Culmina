# Culmina — фінальний контракт перенесення Hybrid у Flutter для Opus



## 1. Мета, повноваження та джерела істини

Реалізуй у наявному Flutter/Dart-застосунку єдиний затверджений **«Hybrid Notion + Journal · ваш напрям»**, під’єднай реальні дані, дії, навігацію та збереження. Це виконання й виправлення проблем, не новий дизайн-аудит. Продовжуй самостійно після внутрішніх контрольних точок; не заверши лише планом, пілотом або QA-звітом.

Цикл: **web-еталон → Flutter-реалізація → зіставні скриншоти/виміри → корекція → виконання дії**. Мета — повне виконання визначеного контракту, не вигаданий відсоток pixel similarity. Owner-приймання відділяй від своїх перевірок.

- Еталон: `design/home-lab/` у **`86873ce343160c860706091e12b257090cc96d94`**.
- Приймання: **`ed2955442110b31eec54fd8db436f1f4e0841993`**, `docs/design/CLAUDE_WEB_QA_FIX_RESULT_2026_10_22.md`. Це документальне приймання без зміни web-коду.
- Зафіксуй фактичні HEAD, гілку, dirty/untracked стан і SDK. Новіший checkout не змінює еталон автоматично. Не reset/clean/stash/checkout поверх чужої роботи, не автоматичний pull, commit або push.
- Якщо локальний web новіший, використай ізольовану read-only копію прийнятого піддерева. Відсутній прийнятий коміт — конкретне обмеження, не дозвіл підмінити джерело. Старий cache-buster `20261020-hybrid7` не є версією замість SHA.
- Не змінюй web, його fixtures або reference-зображення для полегшення збігу.

**Візуальна істина:** прийнятий кінцевий cascade/computed style, геометрія, assets і стани. Не лише `tokens.json` чи перша CSS-декларація; `inventory.json` і старі migration-таблиці можуть бути застарілими.

**Поведінка:** найновіші погоджені продуктові правила та зміст дій web. **Реалізаційна основа:** наявні Dart-моделі, ViewModel, services, repositories, наукові й data-інваріанти. Чинний код не автоматично безпомилковий: виправляй дефекти інтеграції. Але JS-демообчислення та browser storage не замінюють production-логіку. Конфлікт вигляду — виправ за web; handler/state — за погодженою дією; конфлікт бізнес-правил/наукового змісту — зафіксуй без мовчазної зміни формул чи даних.

Прочитай обов’язкові repo-інструкції та лише потрібні skills. Для цього завдання чинні рішення власника: 100% тексту, risk-based перевірки (§6), без старого ліміту «дві корекції» й повного suite після кожної правки. Не переписуй загальні інструкції заради цього винятку. Реальні permissions, hooks і branch protections не вимикай; нерозв’язний конфлікт назви.

## 3. Скінченний обсяг і контрольні точки

Веди один `docs/design/migration/HYBRID_TRANSFER_STATUS.md` та одну evidence-теку. Збережи чужий історичний статус, додай секцію поточного перенесення. Нова dashboard-інфраструктура не потрібна.

На старті сформуй компактний **скінченний реєстр** зі стабільними ID:
`surface/state/transition → web source → Flutter target → required/excluded → visual → functional → evidence`.
Використай наявні інвентаризації, перевіривши delta до прийнятого еталона; не повторюй весь аудит. Детальні стилі й captures збирай за блоками, не всі до початку реалізації.

Обов’язкові всі унікальні композиції, дочірні редактори, діалоги й визначені стани/переходи затвердженого Hybrid: Tonight/Home, Plan, Night/Moon, Weather, Logbook, Library, Settings та інші реально досяжні поверхні. Студійна оболонка, концепт-селектори, галерея шрифтів, рамка телефона та fake system bars виключені.

Збережи native-only GPS, permissions, import, files, export/share, backup/recovery. Їхній вигляд узгоджуй спільними компонентами; без web-аналога статус — «native adaptation», не pixel match. Функції не видаляти через відсутність у прототипі.

Повторення спільної перевіреної композиції можуть мати `covered-by` з обґрунтуванням; унікальну поведінку це не виключає. `N/A` — лише для справді незастосовного критерію. Неперевірене — `pending/blocked`, не PASS. Не скорочуй обсяг заради COMPLETE. Знайдені пропуски еталона додавай; нові ідеї й незалежні старі борги — у відкладений список.

Контрольні точки:

1. Зафіксувати еталон і обсяг; зняти та **відкрити** одну зіставну web/Android-пару, перевірити доступність інструментів.
2. Перенести shared-компоненти та сценарій Tonight → Plan → редактор блока → Apply → Save → повторне відкриття. Виправити спільні причини перед поширенням.
3. Послідовно перенести Night/Moon/Weather, Logbook/Library, Settings та решту реєстру. Залежності можуть змінити порядок, не обсяг.
4. Перевірити останні shared-зміни й наскрізні сценарії; зібрати звичайний release APK і виконати smoke саме цього файла.

Не запитуй приймання кожної дрібної правки; після внутрішньої перевірки продовжуй. Загальне owner-приймання — після результату.

## 4. Протокол візуального підтвердження

### Походження та однакові умови

Використовуй наявні browser/capture helpers і Flutter/Android harness. Не створюй нову платформу тестування. Нативне підтвердження завершеного блоку — справжній Flutter на явно обраному disposable Android-емуляторі, не Flutter Web, HTML-копія або окремий showcase. Host-render із реальними шрифтами допустимий для швидких ітерацій, не замість native-підтвердження.

Знімай цифрові screenshots, не фото камерою. PNG на диску не доводить перегляду: відкривай обидва зображення доступним інструментом зору. Якщо це неможливо, не симулюй visual PASS.

Один manifest на capture-run: web SHA/config, Flutter SHA + fingerprint релевантних dirty-змін, збірка, viewport/app-area/DPR, тема, locale/timezone/units, fixtures і font/text scale. Для кадру — ID, стан, кроки, scroll/focus та відмінності від defaults. Не дублюй усі метадані для кожного PNG.

Web: Chromium, `variant=blend`, `font=native`, text scale 1, browser zoom 1, ізольований контекст. Виміряй **ширину телефонного контейнера** 375/412 через DOMRect; viewport браузера 375 не гарантує телефон 375. Орієнтир прийнятих captures — host 1200×1000 із окремо заданою шириною телефона.

Flutter: та сама логічна app-area, тема, текст, дані, locale, час, одиниці, scroll і focus. Зафіксуй однакову зіставну висоту. Перевір фактично завантажені шрифти, усталені анімації та відповідний стан. Не змінюй параметри особистого телефона.

Виключай лише явно визначені fake/native system bars; app header/footer/текст/дії не обрізай. Збережи оригінали. Не деформуй зображення; перерахунок DPR — лише зі збереженням пропорцій. Геометрію звіряй у логічних одиницях, кольори — також за source/computed style.

Fixtures дозволені лише через існуючі ізольовані adapters у **ті самі production-віджети й маршрути**, не capture-only верстку. Для visual-пари потрібні зіставні presentation-значення; однакові входи demo й реальних формул не завжди дають однакові числа. Не змінюй science заради PNG: domain/production-поведінку перевіряй окремо.

### Покриття без надмірної матриці

- 375 / 100%: кожна унікальна композиція та її визначені візуально відмінні normal/empty/loading/error/selected/expanded/invalid/dirty/dialog стани, де застосовно.
- Dark/Field: усі основні екрани та кожний унікальний стиль форм, діалогів, графіків і контролів у представницькому контексті. Field-діалоги перевірити окремо.
- 412 / 100%: кожний унікальний responsive-layout і зміни переносу, колонок, scroll/footer. Повторні еквівалентні випадки — `covered-by`.
- Shared disabled/focus/pressed/error: на компоненті та в місцях власних overrides. Hover — для підтримуваного pointer-сценарію, не блокер touch-інтерфейсу.

Не будуй повну комбінацію всіх даних, тем і станів. Запиши фактичне покриття; не зараховуй неперевірені комбінації. 125/200%, інші браузери й усі пристрої — не цей прохід.

Для довгих екранів переглянь верх і потрібні нижні scroll-позиції. Наддовгий full-page PNG не замінює viewport-перевірку sticky/footer. Рух і тимчасові повідомлення перевіряй діями/серією кадрів; справжні IME й Back — native-сценарієм.

Reference знімай один раз або перевикористовуй після звірки SHA/умов. Після правки перезнімай зачеплене; перед закриттям блоку — актуальні фінальні пари. Зміна шрифту/shared-компонента/theme може анулювати залежні старі captures: перевір вплив адресно.

### Порівняння та корекція

Сам переглянь side-by-side в достатньому масштабі. Overlay/difference — для підозрілих ділянок; contact sheet — лише навігація. Перевір порядок, групування, зовнішні/внутрішні відступи, baseline/leading/переноси, кольори, controls, іконки, графіки, розділювачі та нижні дії.

Для розбіжності: місце → очікування → вимір → причина → виправлення. Використовуй DOM/computed styles і Flutter bounds. Не компенсуй неправильний шрифт випадковим padding. Дизайн-параметри відтворюй точно; до 1 логічної одиниці — лише пояснене округлення геометрії без накопиченого дрейфу, не загальний допуск. Antialiasing не дорівнює layout-дефекту; неправильна гарнітура/вага/перенос не пояснюється antialiasing.

Перевір застосовані пари текст/фон, focus, потрібні межі й графіки в змінених станах. Регресію контрасту усунь без нового редизайну; не заявляй загальну WCAG-відповідність Field.

Не закривай розбіжності глобальним SSIM/відсотком, маскуванням app-елементів або оновленням golden під неправильну реалізацію.

## 5. Функції: незалежний критерій

Для дій зафіксуй у тому самому реєстрі зв’язок:
`web action/state → route/widget → data source → handler/ViewModel → результат/запис → перевірка`.
Скриншот Save чи callback у коді не доводять збереження. Статуси visual та functional незалежні.

Виконай потрібні сценарії: choose/manage/edit місця, target і rig та оновлення залежних екранів; block draft/validation/Apply/Cancel/Discard/Back; окремий Save плану; autosave/new/copy/Undo/ID; reopen після холодного перезапуску **ізольованої файлової БД**, не лише in-memory. Перевір одиниці/timezone, перегляд іншої ночі без зміни active plan; Weather partial/stale/offline/error/retry/gaps; Logbook result/progress/filters; Settings immediate/Save і persistence; зачеплені native-only дії.

Для Weather додай лише мінімальну відсутню UI-preference через чинний механізм: `rows` за замовчуванням, save/reopen, сумісне читання старих записів і backup без поля. A/B використовують одні реальні дані. Не копіюй browser backup format і не змінюй схему БД заради вигляду.

Не показуй успішне збереження до завершення операції. Loading завершується операцією, тимчасове підтвердження — визначеним переходом, постійна проблема — після усунення причини; не лікуй усе таймером. Перевір ризикові retry/cancel/double tap, швидку зміну контексту й вихід до завершення запиту: стара відповідь не підмінює новий стан, rebuild не стирає ввід.

Неперевірений provider познач `external-unverified` із конкретною зовнішньою залежністю та app-side доказом. Save/Apply/Back/Settings не можна приховати під цим статусом. Native file/share/permission UI потребує наявного Android-інструмента; успішний Flutter-harness не доводить виконання системного діалогу.

Наприкінці запусти звичайний `lib/main.dart` без fixture-overrides. Тестові дані/інструменти не мають підміняти production.

Перед нетривіальним прогоном коротко назви новий ризик; після фіксу повторюй зачеплене, не все. Не створюй тест на кожен padding. Не вимикай/не послаблюй тести заради PASS. Не допускай нових видимих затримок; підтверджені причини в зачепленому сценарії виправляй. Не запускай запити/записи/важкі розрахунки в build, не дублюй listeners/controllers. Без глобальної зміни state management або кешування «про всяк випадок». Debug/емулятор не доводять release-плавності; числове прискорення — лише зіставний profile-вимір на окремо дозволеному фізичному пристрої. Його відсутність назви обмеженням, не «оптимізацію завершено».

## 7. Реалізація, дані та фінальний APK

Використовуй і за потреби виправляй наявні shared-компоненти/services, не дублюй другу систему. Не WebView, не картинки замість UI. CustomPainter — для відповідних графіків, не заміна доступних controls. Явно відтвори Material padding/min-size/shape/overlay/tint/elevation/labels, font metrics, SVG viewBox/stroke й алгоритм градієнта; збережи hit targets, semantics, focus і ліцензії assets.

Native safe areas/IME замінюють web-симуляцію, не додаються двічі. Без fixed-canvas усього застосунку. Не змінюй схему БД, наукову семантику, записи/поля заради layout. Не встановлюй/оновлюй SDK/CLI/plugins і не обходь permissions.

За замовчуванням — **явно обраний disposable-емулятор із синтетичними даними**, не перший підключений device. Особистий телефон, основний пакет і `.dev` захищені. На телефоні заборонені `flutter drive`, uninstall, clear-data, downgrade та автоматична перевстановка. Package suffix і `--keep-app-running` самі не гарантують безпеку. Phone QA/оновлення потребує окремо погодженого безпечного сценарію, перевірених package ID/підпису; backup не припускати. Без цього телефон не чіпай.

Release: використовуй наявний дозволений build-шлях. Без production-ключа не шукай секрети, не створюй/замінюй ключі й production-signing. Наявний дозволений локальний release із тестовим/debug-сертифікатом допустимий із явною позначкою «перевірочний, не магазинний». Якщо такого шляху немає — packaging-blocker, не підміна debug-збіркою.

Для APK запиши source SHA/dirty fingerprint, build command/variant, package ID, ABI, SHA-256, режим і тип підпису. Smoke на сумісному disposable-емуляторі — **саме цей APK**, не стара capture-збірка. Після релевантної зміни коду/ресурсів онови збірку й залежні докази. Не змінюй application ID постійно та не встановлюй APK на особистий телефон у межах цього дозволу.

## 8. Ресурс і продовження

Один виконавець; без повторних повних аудитів іншими агентами. Делегування — лише вузьке й виправдане, без паралельного редагування спільних файлів. Не перечитуй репозиторій/історію після кожної правки; у контексті лише активні пари й потрібні crops.

Після checkpoint онови статус: що зроблено, реальні visual/functional докази й результати команд, кількість обов’язкових pending/failed, блокери, наступний крок. Після compaction/resume прочитай цей контракт і checkpoint, звір робочий стан та продовжуй з першого pending, не починай аудит заново. `/goal`-оцінювач і власний checklist не замінюють докази.

Не повторюй дорогу невдалу команду без нових входів/діагностики. Дві однакові безрезультатні спроби без нових фактів — зупинка саме цього шляху, не ліміт на дві обґрунтовані корекції. За недоступного інструмента, ризику даним, нового продуктового рішення чи фактичного вичерпання квоти збережи точний checkpoint; незалежне безпечне можна продовжити. Не вигадуй залишок квоти, не купуй додаткову й не перемикай акаунти. Промпт не є жорстким лічильником витрат.

## 9. Умови COMPLETE та передача

Виконуються **разом**:

1. Еталон зафіксований і незмінний; реєстр охоплює весь обов’язковий обсяг без самовільних виключень.
2. Для **кожного обов’язкового app-side пункту** visual/functional — PASS або обґрунтоване `covered-by`/незастосовність критерію. **Нуль pending, blocked, fail і неперевірених обов’язкових пунктів.** «Враховано» не дорівнює виконано.
3. Visual PASS підкріплені актуальними переглянутими парами/вимірами та Android-підтвердженням за §4; невиправлених непогоджених відхилень немає. Native-only адаптації не видаються за відсутні web-пари.
4. Дії під’єднані до реальної логіки; визначені сценарії збереження/reopen/errors/retry пройдені. `external-unverified` стосується справжньої зовнішньої залежності, не незробленої внутрішньої дії, і явно обмежує native-приймання.
5. Немає відомих регресій, втрати функцій, нових analyzer/build-помилок у зміненому коді; risk-based перевірки пройдені, сторонні обмеження не приховані.
6. Звичайний release APK без fixtures зібраний із зафіксованим походженням/підписом; саме він пройшов smoke. Релевантних неврахованих змін після перевірок немає.

Інакше — **PARTIAL/BLOCKED** з точним залишком. Зупинка через квоту не означає виконання. Список неперевіреного не перетворює обов’язкову перевірку на необов’язкову.

COMPLETE цього перенесення не означає phone/performance-приймання, усі text scales/пристрої, owner-приймання або готовність до магазину. За виконаних інженерних критеріїв передай результат і зупинись, не вигадуй нові покращення.

Підсумок українською: обсяг і фактичні visual/functional результати, залишкові обмеження, посилання на пари та фінальний APK. Репозиторні документи — за правилами їхньої мови. Без нового великого аудиту.

**Починай із еталона й однієї capture-пари; далі реалізовуй, зіставляй і виправляй до критеріїв завершення.**
