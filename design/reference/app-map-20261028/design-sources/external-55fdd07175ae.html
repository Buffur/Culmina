   6  # Generate design tokens
   7  
   8  ## Establish the target
   9  
  10  - Identify the source palette, target platform or format, theme count, naming convention, and required states.
  11  - If no format is specified, provide a small platform-neutral token model and CSS custom properties.
  12  - Preserve user-provided color values unless derivation is requested. Explain any generated tints, shades, or replacements.
  13  
  14  ## Model the tokens
  15  
  16  1. Separate **primitive tokens** (value-oriented names such as `blue-600`) from **semantic tokens** (purpose-oriented names such as `color-action-primary`).
  17  2. Create only tokens supported by a real use case. Avoid huge interpolated scales by default.
  18  3. Cover the relevant roles: canvas, surface, elevated surface, text, muted text, border, primary action, accent, focus, and requested status states.
  19  4. Keep semantic names stable across light and dark themes; change their mapped primitives rather than their meaning.
  20  5. Do not use transparency to conceal an unknown composited result. When alpha is necessary, document the expected backdrop.
  21  6. Flag high-risk foreground/background pairs for contrast verification. Do not assert WCAG conformance without calculated ratios.
  22  
  23  ## Produce artifacts
  24  
  25  - Show a concise role-to-value mapping and then output the requested code format in a fenced block.
  26  - Keep names syntactically valid for the target and use one authoritative value per primitive.
  27  - Invoke `palette-picker` with the unique source and derived colors that benefit from visual editing. Order foundational neutrals first, then brand/action and status colors; explain this ordering in `reason`.
  28  - When the user edits the palette later, remap tokens by role rather than by array position alone.
