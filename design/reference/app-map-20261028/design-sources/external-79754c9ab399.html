   6  # Design QA
   7  
   8  Use this internal helper to compare a prototype's source design against the rendered implementation before handoff.
   9  
  10  Do not use this skill for broad UX critique, design critique, product audits, or flow reviews. Use [audit](../audit/SKILL.md) for those user-facing requests.
  11  
  12  Use this skill before every Product Design build handoff.
  13  
  14  A passing QA run requires both:
  15  
  16  - a source visual target: Figma node, image, screenshot, mockup, or source capture
  17  - a rendered implementation: local URL, deployed URL, app screen, component, or screenshot
  18  
  19  If either artifact cannot be opened, captured, or compared, write `design-qa.md` with `final result: blocked` and name the blocker. Do not let the build skill hand off as done.
  20  
  21  ## Critical Overrides
  22  
  23  Follow [critical-overrides](../../references/critical-overrides.md).
  24  
  25  ## Workflow
  26  
  27  Compare the intended design to the implementation as a product-quality reviewer, not as a generic aesthetic critic. The output must be a prioritized fix list grounded in evidence from both artifacts.
  28  
  29  Do not write the QA review from memory, code, or file paths alone. Open or capture both the source design and the implementation first, then compare what is actually visible.
  30  
  31  Do not pretend separate image views are side-by-side comparison. Put the source image and the implementation screenshot together in the same comparison input, then judge the visible differences from that combined input.
  32  
  33  Design QA is an iteration loop. The first comparison may pass only when it finds no actionable P0/P1/P2 differences and no visual fixes are made in response.
  34  
  35  When a comparison finds any P0/P1/P2 issue:
  36  
  37  - Record the finding and keep the current result blocked.
  38  - Apply the fix.
  39  - Capture the revised implementation at the same viewport and state.
  40  - Compare the revised capture against the source again.
  41  
  42  A later pass must identify the earlier findings, the fixes made, and the post-fix visual evidence. Build, dependency, lint, deployment, and preview troubleshooting do not count as design-QA iterations.
  43  
  44  1. Identify the comparison target.
  45     - Determine the source design: Figma node, image, design board, screenshot, spec, or mockup.
  46     - Determine the implementation: local URL, deployed URL, app screen, component, screenshot, or code-rendered view.
  47     - Match the same viewport, state, theme, device density, route, content, auth state, and interaction state before judging.
  48     - If artifacts do not represent the same state, call that out first and avoid false precision.
  49  
  50  2. Capture evidence.
  51     - For Figma, use design context and screenshot tools when available.
  52     - For Product Design `mobile-app` template implementations, capture the app viewport itself, not the whole browser page, desktop canvas, or surrounding phone stage. Use `data-testid="device-screen"` / `[data-phone-screen]` for content-only comparisons; use `data-testid="phone-frame"` only when the source visual includes the device bezel.
  53     - Before capturing a `mobile-app` template, run `npm run check:runtime`. Treat a failure as blocking. Do not bypass the check or accept a rasterized or duplicated status bar, device bezel, or home indicator as app content.
  54     - For web/app implementations, follow the Browser Choice rule in [index](../index/SKILL.md#browser-choice). In ChatGPT Work Mode, follow the active build skill's "Previewing prototypes in ChatGPT Work Mode" section before opening a local implementation. Then capture screenshots at the intended viewport.
  55     - Capture additional states when relevant: mobile/desktop, hover/focus/active, empty/loading/error, dark/light, and key responsive breakpoints.
  56     - Save paths or URLs for screenshots when available so findings can cite evidence.
  57     - Capturing screenshots is not enough. Put the source image and the implementation screenshot together in the same comparison input before judging.
  58  
  59  3. Normalize before comparing.
  60     - Align crop, viewport size, scale, and device frame. Do not compare a framed mockup to an unframed page without noting the mismatch.
  61     - Prefer comparing content regions over full browser chrome or surrounding canvas.
  62     - For the `mobile-app` template, force or verify a 1:1 phone-screen capture before judging fidelity. The template scales the device down to fit small browser viewports; use a large enough Playwright viewport for scale `1` and verify `[data-phone-screen]` measures `393 x 852` CSS px before capture. If the screen measures smaller, the screenshot is scaled and is not valid for 1:1 comparison.
  63     - Capture the mobile app with an element screenshot or an explicit clip from the screen element, for example:
  64  
  65     ```ts
  66     const page = await browser.newPage({
  67       viewport: { width: 1400, height: 1200 },
  68       deviceScaleFactor: 1,
  69     });
  70     await page.goto("http://127.0.0.1:8796");
  71     const screen = page.getByTestId("device-screen");
  72     await screen.waitFor({ state: "visible" });
  73  
  74     const box = await screen.boundingBox();
  75     if (!box || Math.abs(box.width - 393) > 1 || Math.abs(box.height - 852) > 1) {
  76       throw new Error(`Expected unscaled mobile screen at 393 x 852, got ${box?.width} x ${box?.height}`);
  77     }
  78  
  79     await screen.screenshot({ path: "implementation-mobile-screen.png" });
  80     ```
  81  
  82     - Normalize image density before comparing. If the source or implementation is `@2x` or otherwise double-density, compare against a same-size normalized copy: either downsample `786 x 1704` source captures to the `393 x 852` CSS target, or capture the implementation at the same density and compare equal pixel dimensions. Record the source pixels, implementation pixels, CSS viewport, and `deviceScaleFactor` in `design-qa.md`.
  83     - Do not file visual findings caused only by density mismatch, browser chrome, canvas padding, or device-frame mismatch. Normalize those first, then judge typography, spacing, color, imagery, and state.
  84  
  85  4. Compare at the right level of detail.
  86     - Use a full-view comparison to judge overall composition, hierarchy, layout, density, and responsive structure.
  87     - Use focused region comparisons when important details are too small to judge in the full-view comparison.
  88     - Choose focused regions from the actual source and implementation. Use them where fidelity depends on precise typography, alignment, imagery, assets, icons, logos, controls, forms, navigation, tables, dense UI, or visible interaction states.
  89     - If no focused region is needed, say why in `design-qa.md`.
  90     - Do not pass QA from a full-view comparison alone when important details are not clearly readable.
  91  
  92  5. Review systematically.
  93     - Read [qa-rubric](./references/qa-rubric.md) when the QA pass spans more than a quick visual check.
  94     - Check information architecture, layout, spacing, typography/fonts, color, imagery/image quality, icons, copy, affordances, interaction states, responsiveness, accessibility, and polish.
  95     - Always make a specific pass over the five required fidelity surfaces: fonts/typography, spacing/layout rhythm, colors/tokens, image quality, and copy/content. Do this even if the user did not name those areas explicitly.
  96     - If the mock does not address some issue you're seeing (e.g. a null state), call that out as a separate finding as a shortcoming of the mock to be addressed.
  97     - Your other goal is to decide whether the implementation "looks as good" as the mock. If there are stylistic problems, call them out. If the user's prompt is leaking into the implementation (vs letting the app stand on its own), call that out as well.
  98     - Distinguish design drift from intentional product/code constraints. If a deviation may be intentional, phrase it as a question or assumption.
  99  
 100  6. Produce a fix-oriented QA report.
 101     - Lead with findings, ordered by severity and user impact.
 102     - For each finding include: severity, location, what differs, evidence, why it matters, and the concrete fix.
 103     - Include exact CSS/component/token suggestions when the implementation context is available.
 104     - Separate objective mismatches from subjective polish recommendations.
 105     - Do not say a design matches, is done, or is as good as it can get until the required fidelity surfaces have been checked and any remaining differences are explicitly classified as acceptable, expected, or still actionable.
 106     - End with a concise implementation checklist.
 107  
 108  ## Required Fidelity Surfaces
 109  
 110  Every QA report must explicitly evaluate these surfaces:
 111  
 112  - Fonts and typography: family, fallback, weight, size, line height, letter spacing, antialiasing, hierarchy, wrapping, truncation, and whether display text and small UI text use appropriate optical weights. It is incredibly important to check fonts carefully for fidelity, including looking up similar typefaces or using image analysis to find the font differences.
 113  - Spacing and layout rhythm: frame size, crop, alignment, margins, padding, grid tracks, section gaps, component spacing, radii, shadows/elevation, and vertical rhythm.
 114  - Colors and visual tokens: sampled or inferred palette, gradients, opacity, contrast, semantic state colors, foreground/background balance, and whether CSS tokens map to the source design.
 115  - Image quality and asset fidelity: subject correctness, crop, scale, sharpness, compression, transparency halos, masking, background treatment, raster-vs-vector appropriateness, and whether generated assets match the source art direction. Fail QA if logos, illustrations, decorative marks, product imagery, non-standard icons, or other visible image assets from the visual target were replaced with custom inline SVG, handcrafted SVG, HTML elements, div/span shapes, CSS drawings, gradients, emoji, text glyphs, placeholder shapes, or code-native approximations.
 116  - Copy and content of app-specific text
 117  
 118  ## Severity
 119  
 120  - `P0`: Blocks core use, severe accessibility failure, broken layout, or impossible task.
 121  - `P1`: Major design mismatch or usability regression likely to be noticed by users.
 122  - `P2`: Moderate visual drift, inconsistent state, responsive issue, or fixable polish gap.
 123  - `P3`: Minor refinement that improves fidelity but does not block acceptance.
 124  
 125  Treat viewport overflow that hides persistent app controls, and mismatches that materially change above-the-fold content, major-region proportions, text wrapping, or interface density, as P2 or higher.
 126  
 127  ## Output Format
 128  
 129  Use this structure unless the user asks otherwise:
 130  
 131  ```markdown
 132  **Findings**
 133  - [P1] Short issue title
 134    Location: screen/component/selector/file if known.
 135    Evidence: design does X, implementation does Y.
 136    Impact: why this matters.
 137    Fix: concrete change.
 138  
 139  **Open Questions**
 140  - Any ambiguity about intentional deviations, unavailable states, or missing artifacts.
 141  
 142  **Implementation Checklist**
 143  - Ordered fixes that can be executed directly.
 144  
 145  **Follow-up Polish**
 146  - P3 refinements that can improve fidelity after handoff.
 147  ```
 148  
 149  If there are no substantive mismatches, say that clearly and list any residual test gaps.
 150  
 151  When this skill is used before handoff, save the latest QA report as project-root `design-qa.md`.
 152  
 153  `design-qa.md` must include:
 154  
 155  - source visual truth path
 156  - implementation screenshot path
 157  - viewport
 158  - source and implementation pixel dimensions, CSS size, and density normalization used
 159  - state
 160  - full-view comparison evidence
 161  - focused region comparison evidence, or why it was not needed
 162  - findings
 163  - comparison history for every P0/P1/P2 iteration: earlier findings, fixes made, and post-fix visual evidence
 164  - final result
 165  
 166  For ChatGPT Work Mode builds, `design-qa.md` must include the browser-rendered implementation screenshot, viewport, primary interactions tested, console errors checked, and final result. If browser-rendered evidence is missing, `final result` is `blocked`.
 167  
 168  `final result` must be exactly `passed` or `blocked`.
 169  
 170  Use `passed` when there are no actionable P0/P1/P2 findings. P3 findings may remain as follow-up polish.
 171  Use `blocked` when actionable P0/P1/P2 findings remain and name the blocker.
 172  
 173  Return the file path with the QA report.
